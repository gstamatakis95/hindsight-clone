# WP-17 plan: a retag during a retain or reprocess must not lose facts

## Problem
`docSuperseded` treats a document whose tags differ from the run's payload tags as owned by a newer retain.
UpdateDocument (`docs.Retagger.Retag`) changes only the tags. So a retag that lands while a retain or reprocess
job runs makes the job stop as superseded after its first batch, or before it starts. The rest of the chunks
are never extracted and `extracted_at` stays unset. The retag_document job queued behind it only retags the
units that already exist, so those facts are lost.

## Files
- `internal/engine/retain/retainer.go`:
  - Split the ownership check. A different blob key or different overrides means a real owner change, which
    supersedes.
  - If only the tags differ, the run adopts the document's current tags (`rn.tags`). It does this both in the
    pre-check and under the Seq lock in `checkOwner`, and keeps going.
  - `RetainResult.Scopes` is recomputed after the run.
- `internal/engine/retain/retag_test.go` (new): the regression tests.
- `internal/engine/retain/ownership_test.go`: `hookedRetainer` takes a batch size, plus the overrides test.
- `internal/engine/retain/ownership_tags_test.go`: the older-run test asserts the invariant (no stale tags)
  rather than `Superseded`.
- `internal/adapter/gateway/client.go` + `overflow_test.go`: three new overflow markers.
- `internal/porttest/reads_suite.go`: the `testRdErrorRegimes` doc comment now matches what is tested.
- `docs/decisions/807-retain-run-ownership.md` (updated) and `docs/decisions/1700-retag-adopted-by-running-retain.md`.

No interface or constructor changes.
