# CCR WP-19-1 — `UnitRepo.SetDocumentTags` replaces only the document-derived tags

Status: APPROVED by the orchestrator (final review B, H1); implemented in WP-19

## Problem
A unit's tags are the document's tags plus its own extra tags. Today the only extras are the `key:value` label
tags that retain writes for `entity_labels` with `write_to_tags` (`retainer_write.go`, `unit`). A retag
(`UpdateDocument` → `retag_document`) called `SetDocumentTags(doc, newTags)`, which overwrote every unit's
tags with the new document tags. That silently dropped the label tags, on live and archived units.

## Exact diff
`internal/port/repos.go`:

```diff
-	// SetDocumentTags rewrites the tags (and seq) of every live unit of a document, clears their
-	// consolidated_at and consolidation_failed_at (callers delete the old observations with
-	// EvidenceRepo.DeleteCiting), and returns their ids.
-	SetDocumentTags(ctx context.Context, b BankRef, doc DocumentID, tags []string, seq int64) ([]UnitID, error)
+	// SetDocumentTags replaces the document-derived tags of every unit of a document, live and archived:
+	// each unit's tags become normalize((tags − oldTags) ∪ newTags), so a unit's own extra tags (the
+	// write_to_tags label tags) survive. On the live units it also sets seq and clears consolidated_at
+	// and consolidation_failed_at (callers delete the old observations with EvidenceRepo.DeleteCiting).
+	// It returns the live units' ids. Both tag lists must be normalized (domain.NormalizeTags), else
+	// domain.ErrInvalidArgument. Passing the same list twice leaves the tags as they are, apart from
+	// adding any of them a unit lacks, and only resets the stamps.
+	SetDocumentTags(
+		ctx context.Context, b BankRef, doc DocumentID, oldTags, newTags []string, seq int64,
+	) ([]UnitID, error)
```

Postgres implements it as one `UPDATE` per table (`memory_units`, `memory_units_archive`), scoped by tenant,
bank and document. Each sets
`tags = ARRAY(SELECT DISTINCT t FROM unnest(tags || @new_tags) t WHERE t <> ALL(@old_tags) OR t = ANY(@new_tags)
ORDER BY t COLLATE "C")`. The `"C"` collation sorts by byte, the same order Go's `slices.Sort` uses in
`domain.NormalizeTags`. `ARRAY(...)` gives `'{}'` rather than NULL when nothing is left. The fake applies the
same formula with `domain.NormalizeTags`.

## Callers
The card suggested that the retag job pass "the document's previous tags", read under `tx.Seq` in `Apply`.
That is not possible: `Retag` (the API side) has already written the new tags to the document row by the
time the job runs, and the job payload is not readable from `domain.Operation`, so a failed or cancelled
job's old tags could not be recovered. So the units' tags are rewritten in `Retag`'s own transaction,
together with the document row, under `tx.Seq`. See decision 1900.

- `internal/engine/docs/retag_impl.go`:
  - `Retag`, on a real change: after `tx.Seq`, re-read the document and call
    `SetDocumentTags(d.Tags, want, seq)` in the same transaction as `Documents().SetTags`.
  - `Apply` (retag_document): call `SetDocumentTags(cur, cur, seq)` with the document's current tags. This
    resets the stamps again, because a consolidation may have run in between. It returns the ids for
    `DeleteCiting`. It is idempotent.
- Test callers: `internal/porttest/{curation_suite,store_wp01_suite}.go`, `internal/fake/{store_fake,review}_test.go`,
  `internal/adapter/postgres/followup_test.go`, `internal/engine/consolidate/concurrency_test.go`.

## Affected WPs
WP-19 only (adapter, fake, porttest, docs engine, regenerated mocks). No proto, schema or migration change.
