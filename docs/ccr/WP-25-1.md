# CCR WP-25-1: BankRepo.LockTenantConfig

**Requested by:** WP-25 (review finding: concurrent UpdateTenantConfig calls lose an update).

**Change:** one additive method on `port.BankRepo` in `internal/port/repos.go`:

```go
// LockTenantConfig locks the tenant's config for the rest of the transaction, whether or not one is
// set, so a read-modify-write (LockTenantConfig, TenantConfig, SetTenantConfig) serializes with any
// other that locks it too (Postgres: pg_advisory_xact_lock). Plain TenantConfig reads never wait on it.
LockTenantConfig(ctx context.Context, tenant string) error
```

- Postgres: a new sqlc query, `TenantConfigLock`, runs
  `SELECT pg_advisory_xact_lock(hashtextextended('tenant_config/' || $1, 0))`.
- Fake: a no-op, because fake transactions are already serialized.
- Mocks: regenerated with `make gen`.
- Contract case: `porttest:BanksTenantConfigLockSerializes`.
- Caller: `bank.tenantAdmin.UpdateTenantConfig` takes the lock before reading.

**Why not adapter-only:**
- `TenantConfig` is read on hot paths: `config.Resolver`, the retain ingestor and the linker. Locking it
  `FOR UPDATE` would serialize every request of a tenant.
- A row lock also covers nothing before the tenant's first config write, because no row exists yet.
- An advisory lock needs no row and only the config writers take it.

**Impact:** additive. No schema or proto change, and `buf breaking` is unaffected. Any other implementation
or decorator of `port.BankRepo` must add the method. A tracing wrapper from WP-24, if it wraps BankRepo, is
one example.

**Ruling:** pre-approved by the orchestrator for WP-25 (one additive port method); see decision 2500.
