# CCR WP-08-2 — Persist a retain item's observation scopes

Status: superseded by the Phase 2 CCR batch (WP-15). The `documents.observation_scopes` column and
`domain.Document.ObservationScopes` are approved; the proposed batch read `ScopesFor` is rejected. Until WP-15
merges, WP-08 carries the scopes in the job payload and writes them through `retain.DocumentScopesWriter`
(decision 808).

## Problem
`RetainItem.observation_scopes` picks the scope fan-out that the item's units consolidate under. WP-08
validates it synchronously (ALL_COMBINATIONS over `max_combinations` is INVALID_ARGUMENT) and carries it in the
`retain_document` payload. However, no table stores it:
- the documents table has no column for it;
- `memory_units` has no column for it;
- `domain.Document` and `domain.Unit` have no field for it.

So the consolidator (WP-10), which reads units through `UnitRepo.Unconsolidated`, can only apply the bank's
`default_observation_scopes`. A per-item scope choice is validated and then ignored.

## Exact diff
1. Migration: `ALTER TABLE documents ADD COLUMN observation_scopes jsonb` (NULL = the bank default).
2. `internal/domain/unit.go`:

   ```diff
    type Document struct {
    	...
    	// BlobKey is where the original text lives.
    	BlobKey string
   +	// ObservationScopes is the retain item's scope fan-out; nil = the bank default.
   +	ObservationScopes *ObservationScopes
   ```

3. `DocumentRepo.Upsert` stores it and `Get` returns it (adapter, fake, porttest).
4. WP-08 sets it on Upsert. That is a one-line change in `ingestor.go`, `write`.
5. WP-10 resolves a unit's scope mode from its document (units carry `DocumentID`). A batch read such as
   `DocumentRepo.ScopesFor(ctx, b, docs []DocumentID)` would avoid N+1 reads. This is for WP-10 to propose.

## Affected WPs
- WP-01 / WP-02 follow-up: migration, adapter, fake, porttest.
- WP-08: one line.
- WP-10: reads it.
- WP-13: ReprocessDocument replays it.
